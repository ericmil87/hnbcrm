# Canal WhatsApp: Meta Cloud API e bridge (wuzapi/whatsmeow)

> Histórico técnico movido **verbatim** do `CLAUDE.md` da raiz em 22/10/2026 (snapshot do commit 1f51a2f). Ordem = ordem de versão. Pegadinhas que mudam a forma de codar foram destiladas em `.claude/rules/`; este arquivo é a fonte completa, para ler quando se mexe nesta área.

## Estado atual

Dois transportes no mesmo canal `whatsapp` (`channelConfigs.provider`), ingest/dispatch em `convex/whatsapp.ts` e `convex/bridge.ts`, parsers puros em `convex/lib/bridge*.ts`, exclusividade do número, histórico do aparelho, ban/logout e cron de saúde (T02). Tipos de mensagem novos do bridge e revoke/edit estão em `ai-attendant.md` (v0.70, item 3).

## Decisões, pegadinhas medidas e histórico

### WhatsApp channel

**WhatsApp channel:** Per-organization channel configs (`convex/channelConfigs.ts`, `channelConfigs` table) with `provider: "meta" | "bridge"` — two transports on the same `whatsapp` channel. `meta` = official WhatsApp Cloud API (Graph API, 24h service window, message templates); ingress at `GET/POST /webhooks/whatsapp` (`convex/whatsapp.ts`). `bridge` = self-hosted wuzapi gateway (WhatsApp Web protocol via whatsmeow, QR pairing, no 24h window, no templates); ingress at `POST /webhooks/bridge` verified by HMAC-SHA256 via env `WA_BRIDGE_HMAC_SECRET` (`convex/bridge.ts`). Managed provisioning: envs `WA_BRIDGE_DEFAULT_URL` + `WA_BRIDGE_ADMIN_TOKEN` (both set = "Servidor HNBCRM" default in the provisioning form — user only types a display name; admin token never leaves the server; advanced users can still point to their own gateway). Bridge is opt-in per org and carries a permanent-ban risk (unofficial protocol, violates WhatsApp ToS). Key files: `convex/bridge.ts`, `convex/lib/bridgeParse.ts` (pure parser), `convex/lib/bridgeSend.ts` (text), `convex/lib/bridgeMedia.ts` (media), `convex/lib/bridgeSession.ts` (QR/status/provisioning). Outbound dispatch in `convex/whatsapp.ts` branches by provider (voice notes are transcoded to ogg/opus via the Whisper service's `/convert`). Typing presence and delivery/read receipts flow both ways (`sendTypingState`, `markConversationRead`, `ChatPresence`/`ReadReceipt` webhook events). UI in `src/components/settings/channels/` (`ChannelsPanel`, `ChannelCard`, `ChannelConnectCard`, `QrCodeConnectForm`, `MetaForm`, `BridgeQrModal`; + `ChannelHealthPanel` with 7-day delivery stats).

**Connection code UI (fv2-21):** pairing in the UI goes through `startBridgePairing` / `pollBridgePairing` only (`getBridgeQrCode` is no longer used by the UI; it stays in the backend for compatibility). `PairingPanel` offers two tabs: "Conectar com código" (default on narrow or coarse-pointer screens; phone field with the org default country, `linkingCode` shown as `XXXX-XXXX` with a copy button, valid ~2 min, "Gerar outro código" enabled after 150 s, poll every 4 s for up to 3 min, last code kept between polls, `attemptsLeft`/`error` from the server shown as-is) and "Usar QR code" (default on desktop, poll while open, renews itself). Pure rules in `src/lib/channelConnect.ts`. `provisionBridgeChannel` is called without `webhookUrl`: the server builds it from `CONVEX_SITE_URL` (must exist in PROD). The QR and the code are never persisted or logged.

### Bridge — mensagem do aparelho, histórico e exclusividade do número (v0.56)

**Bridge — mensagem do aparelho, histórico e exclusividade do número (v0.56):** três coisas que faltavam para o inbox bater com a conversa real. (1) **`fromMe` entra como `outbound`:** o parser descartava todo `Info.IsFromMe` para evitar o eco do próprio CRM, mas o WhatsApp multi-device usa o MESMO evento para o eco e para o que um humano digita no app do celular — descartar os dois fazia a conversa divergir (e o atendente IA lia um histórico incompleto). Agora vai para `conversations.internalReceiveDeviceMessage` (`metadata.via:"device"`, sem `senderId`, NÃO mexe em `lastInboundAt`/`unreadCount`, NÃO enfileira a IA nem transcrição/visão; o eco morre na idempotência de `externalId`). O telefone sai do `Chat` (o `Sender` somos nós) e o `PushName` é descartado (é o nosso — renomearia o contato). Reação nossa e grupo seguem ignorados. (2) **Histórico do aparelho, POR NÚMERO, opt-in default OFF** (`channelConfigs.bridgeHistoryEnabled/Limit/Days`, 100 msgs/conversa e 7 dias): o wuzapi guarda as mensagens numa tabela própria quando o instance tem `history > 0`, e cada linha traz o evento whatsmeow ORIGINAL — a importação reusa `parseBridgeEvent` e o ingest inteiros, então re-sincronizar não duplica. `lib/bridgeHistory.ts` (puro) + `bridge.setBridgeHistoryConfig`/`syncBridgeHistory`/`internalImportBridgeHistory`; UI no card do número. **Importa só `fromMe`, de propósito:** a recebida sempre chegou pelo webhook, e reinjetá-la passaria por `internalReceiveMessage`, que enfileira o atendente — numa org em autopilot a IA responderia no WhatsApp a uma pergunta de dias atrás. **Pegadinhas do wuzapi medidas contra o gateway real** (fixtures nos testes): o campo é `data_json` (snake_case, o alias `datajson` só existe no SELECT interno); a coluna `timestamp` da linha é o instante da GRAVAÇÃO, não o da mensagem (num HistorySync as 50 linhas vieram com o mesmo carimbo sendo de meses atrás — a hora real sai de `data_json.Info.Timestamp`); conversa sem histórico devolve `{"code":200,"data":null}`, que tratado como erro fazia TODA a varredura falhar. O HistorySync sob demanda é best-effort de verdade (pedimos 100 e vieram 50, todas antigas). (3) **Um número = uma conta:** `channelConfigs.bridgePhone` (dígitos) + índice `by_bridge_phone` DEPLOYMENT-WIDE. O mesmo número pareado em duas orgs faz cada mensagem do contato ser ingerida nas DUAS — vazamento entre inquilinos, não só ruído. Ao ficar "connected", `claimBridgePhone` (dentro de `internalRecordHealthCheck`, MESMA transação, então não há janela com os dois ativos) desativa os outros canais com aquele número, audita na org DESLOCADA (severity `high`), pausa as campanhas dela e agenda `internalLogoutBridgeInstance` (`POST /session/logout` com o token da própria instância — desvincula o aparelho; `/session/disconnect` só derruba o socket e não serve). `deleteChannelConfig` também agenda o logout: era ELE que criava instâncias órfãs logadas para sempre. **Pegadinha decisiva:** `GET /session/status` devolve `jid: ""` mesmo logado (medido em 3 instâncias) — por isso `displayPhoneNumber` nunca era preenchido em canal bridge; o número sai de `GET /admin/users` (`phoneFromAdminUsers`), disponível só no gateway GERENCIADO, então em self-hosted a chave fica vazia e a regra não dispara. Aviso genérico no modal do QR antes de escanear (o número só é conhecido depois) + banner nomeando as contas deslocadas, sem auto-close. **(4) Correção de fundo:** `buildBridgeConnectRequest` mandava `Subscribe: ["Message"]` por padrão e o `Connect()` do wuzapi faz `UPDATE users SET events=$1` — todo reconnect REESCREVIA a assinatura feita no provisionamento, e por isso os recibos de entrega/leitura estavam mortos desde 2026-08-07 (todos os outbound travados em `sent`). Agora existe `BRIDGE_WEBHOOK_EVENTS`, compartilhada entre connect e provisionamento. Ops: `channelConfigs:internalResolveBridgePhone`/`internalBackfillBridgePhone`, `bridge:internalApplyBridgeHistoryConfig`. Testes: `bridgeDeviceMessages.test.ts`, `bridgeNumberExclusivity.test.ts`, `lib/bridgeHistory.test.ts`.

### Ban/logout do bridge + cron de saúde dos canais (T02, v0.69)

**Ban/logout do bridge + cron de saúde dos canais (T02, v0.69):** `LoggedOut`/`TemporaryBan`/`ClientOutdated` eram assinados em `BRIDGE_WEBHOOK_EVENTS` e descartados pelo parser — ban só aparecia quando o cliente reclamava. Agora viram `kind:"session_event"` em `lib/bridgeParse.ts` (envelope `{type, event}` confirmado no `wmiau.go` do wuzapi; `TemporaryBan.Expire` vem em ns → `expiresInMs`; `Disconnected`/`Connected` seguem ignorados de propósito — o socket cai e volta). `channelHealth.internalRecordSessionEvent` → emissor único `emitChannelSessionLost` (`lib/channelHealthSignals.ts`, onde a T10/Sentinela pluga `opsAlerts`): grava `bridgeSessionState` (`logged_out`|`temporarily_banned`|`outdated`, ou `disconnected`/`banned` quando vem do cron), `bridgeSessionDetail`, `bridgeSessionExpiresAt`; pausa campanhas pelo MESMO `pauseCampaignsForChannel` do `claimBridgePhone` e publicações via `pausePostCore`; audit `high`; notificação `channel_session_lost` (só sino, pref `channelSessionLost` default ON) para membros não removidos com `settings:manage` (inclusive "busy"); webhook `channel.session_lost` (telefone mascarado; sem token/URL/instância). **O emissor NÃO mexe em `channelConfigs.status`:** o webhook do bridge descarta todo evento de canal `status !== "active"`, e gravar `"error"` perderia as mensagens de cliente quando o socket volta sozinho (até 15 min) — quem trava envio é `bridgeSessionState` via `isSessionLostState` (follow-up adia com backoff, boas-vindas do site pula, `groupPostWorker` pausa, campanha já travava em `!== "connected"`). Dedupe por `bridgeSessionAlertedAt`, limpo por `internalRecordHealthCheck` quando volta a `connected` (que preserva o `claimBridgePhone` da v0.56); estado mais específico vindo depois (cron `disconnected` → webhook `logged_out`) re-notifica. **Cron `channel health` (15 min, `internalChannelHealthTick`):** pagina `channelConfigs` de 50 em 50 (filtro de provider em memória, auto-reagendamento por cursor), sonda `GET /session/status` com o mesmo builder/parser da health check manual (8 s × 50 cabe nos 10 min), pula Meta/desativado/org demo/canal que nunca conectou; fora do ar marca `bridgeUnhealthySince` na 1ª vez e alerta na observação seguinte se ≥ 10 min; erro de probe NÃO conta como queda; nunca rebaixa estado grave do webhook. **Pegadinhas:** haverá um burst único de alertas pós-deploy nos canais fora do ar há dias; instância provisionada antes da v0.56 só reassina os eventos graves ao reconectar; o wuzapi também emite `ConnectFailure` (não assinado — candidato à T10). Fixture `__fixtures__/bridgeSessionEvents.json` é SINTÉTICA. Testes: `bridgeSessionEvents.test.ts` (19).


### Presença global "invisível" — o celular do cliente volta a tocar (v0.72, 03/11/2026)

**Presença global "invisível" — o celular do cliente volta a tocar (v0.72, 03/11/2026):** caso real em produção: o celular do titular parou de tocar para o WhatsApp depois que o número foi pareado ao HNBCRM. Causa confirmada no código-fonte do wuzapi (`wmiau.go`, `sendAutomaticPresence`) e nos logs do gateway (39 ocorrências em 7 dias, uma a cada reconexão do socket): o gateway anuncia `PresenceAvailable` em todo `Connected`, `PushNameSetting` e sync crítico do app state, e o WhatsApp **silencia o telefone enquanto um aparelho vinculado está `available`**. O HNBCRM nunca mandava presença global (só `/chat/presence` de digitação). Correção em duas camadas: (1) **por canal, ligado por padrão** — `channelConfigs.bridgePhoneNotifications` (ausente/`true` = celular toca → mandamos `POST /user/presence {"type":"unavailable"}`; `false` = legado, `available`); helpers puros `buildBridgeGlobalPresenceRequest`/`desiredBridgePresence` em `lib/bridgeSend.ts`; `channelHealth.internalBridgeApplyPresence({configId})` (best effort, timeout 10 s, nunca lança, pula canal não-bridge/inativo/demo) é agendado ~2 s depois do pareamento em `getBridgeQrCode` (o wuzapi manda `available` dentro do próprio handler de `Connected`, o nosso tem de chegar depois), em "Testar conexão", ao mudar o toggle em `updateChannelConfig` (campo em `BRIDGE_FIELDS`, auditado), e **reafirmado a cada tick do cron de saúde** (15 min) para todo canal conectado — não assinamos `Connected`, então a reconexão é coberta pelo tick. UI: card "Notificações no celular" em Configurações → Canais (só bridge). (2) **no gateway** — a imagem oficial `asternic/wuzapi` ≥ 1.0.9 (ago/2026) aceita `WUZAPI_AUTO_PRESENCE=unavailable` ("preserve primary-phone push notifications"); setar no compose do servidor gerenciado fecha a janela entre a reconexão e o próximo tick. **Digitação com presença "invisível":** o WhatsApp pode não repassar o `composing` de um aparelho vinculado que está `unavailable`, então, quando a opção está ligada, a digitação humanizada do atendente/agendadas (`dispatchViaBridge`) e o "digitando…" do operador (`internalBridgeSendPresence`) viram um parêntese `available → composing → envio → unavailable` (helpers em `lib/bridgePresence.ts`; best effort, timeout 4 s), e **todo envio pelo bridge fecha com `unavailable`** mesmo sem digitação — o operador que digita e fecha a aba sem `paused` não deixa o número "online" até o próximo tick; com a opção desligada nada muda. O tick de saúde tem deadline de 420 s (reagenda com `skip` na mesma página) para caber nos 600 s da action; depois do pareamento a presença é aplicada em 2 s e de novo em 30 s (o wuzapi reanuncia `available` em `PushNameSetting`/app-state sync). Decisão: **ler uma conversa no inbox continua marcando como lida no WhatsApp** (`markConversationRead` → `/chat/markread`): equipe leu = cliente vê o visto, e a notificação daquele chat some do celular de propósito; o atendente IA não marca nada como lido. Doc drift corrigido na regra: `BRIDGE_WEBHOOK_EVENTS` nunca incluiu `ChatPresence`. Testes em `bridgePresence.test.ts`.

### Reconexão do WhatsApp (v0.78)

**Pareamento por código (`POST /session/pairphone`).** Adapter puro em `lib/bridgeSession.ts`: `buildBridgePairPhoneRequest(baseUrl, token, phoneE164Digits)` (POST, header `token`, corpo `{"Phone": "<só dígitos>"}`) e `parseBridgePairPhoneResponse(json)` → `{linkingCode?, loggedIn?, error?}`. Tolerante a caixa e a `data`/`Data` (`LinkingCode`, `linkingCode`, `Code`, `code` string); o `code` NUMÉRICO do envelope do wuzapi é o status HTTP e nunca vale como código. Normaliza para `XXXX-XXXX` (insere o traço quando o gateway devolve 8 caracteres). Quem usa é o fluxo "Reconectar" do Telegram (`rc:<channelConfigId>`): `connect` → `pairphone` → acompanhar `/session/status` até `loggedIn`.

**O que assumimos (nunca exercitado ao vivo antes da v0.78).** O handler upstream não checa `IsConnected`, então o `connect` vem ANTES; o código vale ~160 s (a janela do websocket de login do whatsmeow, a fonte não dá o número exato); o telefone passado é o do próprio número do canal (`channelConfigs.bridgePhone`; self-hosted sem ele cai no QR). O gateway pode rejeitar `pairphone` numa sessão já pareada (`loggedIn` volta verdadeiro).

**Core compartilhada (v0.78).** O passo de reconexão (status → connect → QR ou `pairphone` → com `loggedIn`: número, `internalRecordHealthCheck(connected)` com `claimBridgePhone`, presença +2 s/+30 s) mora em `convex/lib/channelReconnectCore.ts` (`runBridgeReconnectStep`), usada pela action web `channelConfigs.getBridgeQrCode` (mesmo comportamento) e pelo fluxo do Telegram (`convex/telegramReconnect.ts`). Os helpers HTTP do bridge foram para `convex/lib/bridgeGateway.ts`. Só `logged_out`/`disconnected` são reconectáveis (`isReconnectableState`). Detalhes do fluxo: `docs/architecture/telegram.md` (F5a).

**Pareamento web por código (fv2-06).** `channelConfigs.startBridgePairing({ configId, mode: "qr"|"code", phone? })` e `pollBridgePairing` (settings:manage + conta com e-mail, via `internalGetPairingContext`) chamam a mesma core (`runBridgeReconnectStep`). `mode:"code"` normaliza o número com `normalizeCampaignPhone` + `settings.defaultCountryCode`, recusa < 10 dígitos antes do gateway e consome UMA tentativa do teto de 3/h por canal (`lib/pairingQuota.ts`, linha de `telegramReconnects` COMPARTILHADA com o Telegram: `internalConsumePairingAttempt` só mexe em `hourStart`/`attempts`, nunca em `token`); a 4ª na hora devolve erro PT-BR com o horário de liberação no fuso da org. QR não consome cota; o poll (`phase:"poll"`) nunca pede código novo. Código e QR só na resposta (nunca em log, auditoria ou doc); auditoria `channel.pairing_requested` com `via:"web"`, sem telefone. `getBridgeQrCode` (Configurações) segue com sua forma e permissão, mas passa pela mesma função interna de início. `provisionBridgeChannel` aceita `webhookUrl` opcional: sem ele o servidor monta `bridgeWebhookUrl(CONVEX_SITE_URL)` (`/webhooks/bridge`). A tentativa volta (`internalRefundPairingAttempt`) quando o gateway falha ou nenhum código sai (ex.: canal já conectado); a auditoria só é gravada quando um código sai; `banned`/`temporarily_banned`/`outdated` e tentativa do Telegram em curso (`token` + `until`) são recusados antes do gateway. Pendência: `getBridgeQrCode` ainda não exige e-mail; o PR que trocar Configurações para `startBridgePairing` (fv2-21) fecha isso. Testes: `bridgePairing.test.ts`, `lib/pairingQuota.test.ts`.

**Validado ao vivo no gateway gerenciado (03/11/2026, sonda com instance descartável criado por `POST /admin/users` e apagado por `DELETE /admin/users/{id}/full`, nenhum canal real tocado):** `POST /session/connect` (`Immediate:true`) responde `{code:200, data:{details:"Connected!", jid:""}}`; `GET /session/status` devolve `connected:true, loggedIn:false` antes do pareamento; `POST /session/pairphone {"Phone":"<dígitos>"}` com header `token` responde `{code:200, success:true, data:{LinkingCode:"XXXX-XXXX"}}` (já com o traço; sem `LoggedIn`); `GET /session/qr` continua disponível ao mesmo tempo (`data.QRCode` data URI PNG de ~1,8 KB, `passkeyPending`, `publicKey`). **Ainda não medido** (exige completar um pareamento real num aparelho): validade exata do código, se um segundo `pairphone` invalida o primeiro, ritmo de troca do QR, rótulos atuais do app e se `resolveBridgePhone` acha o número logo após o pareamento por código. Reconexões repetidas sinalizam ban: o fluxo limita a 3 tentativas por hora por canal.

### Número com a grafia errada, retry e "sem WhatsApp" (nov/2026)

**Caso real (3 em 30 dias em PROD, mesma forma):** `error sending message: no LID found for 5531990001234@s.whatsapp.net from server`. O contato estava endereçado com a grafia de 13 dígitos (9 extra), a conta WhatsApp existe como `553190001234`. O whatsmeow devolve `no LID found` quando o usync responde e o WhatsApp não tem conta naquele JID exato: "não registrado" e "registrado na outra grafia" têm o MESMO texto. Falha de lookup tem texto próprio (`failed to get user info … to fill LID cache: …`, inclusive `429: rate-overlimit`) e falha do store local outro (`failed to get LID for PN …`). Destinatário que bloqueou o remetente não aparece em nenhum erro. Regra fixa tipo "DDD ≥ 29 perde o 9" é falsa (há contraexemplos reais): só a resposta do gateway vale (`checkBridgeNumber`).

**Restrição do dono:** proteger as contas dos clientes contra ban e os clientes contra mensagem duplicada. Nunca reenviar para grafia que o WhatsApp disse não existir, nunca laço, poucas consultas, nunca reenviar automaticamente o que pode já ter saído; na dúvida não envia e avisa um humano.

**Classificação (`lib/bridgeSendError.ts`, pura).** `recipient_not_found` (`no LID found`); `transient` (só o provadamente anterior ao envio: falha do lookup/store de LID, conexão recusada, DNS); `rate_limited` (429, `rate-overlimit`); `session` (401/403, ou texto de sessão fora de 5xx); `ambiguous` (PODE já ter sido entregue: `network:true`, qualquer 2xx sem id reconhecido, timeout/EOF/reset, `websocket disconnected before message send returned response`, 5xx — inclusive com texto de sessão —, "Gateway não retornou o id", exceção inesperada); `permanent` (padrão, 4xx e desconhecido). A classe fica em `metadata.deliveryErrorKind`; `metadata.deliveryPreSend` marca falha provadamente anterior ao envio (recusa local: canal desconectado, gate, opt-out, anexo, configuração; HTTP 4xx). `bridgeRetryPlan`: transient = 3 envios no total (30 s, 2 min); rate_limited = 1 retry em 15 min; os demais nunca reenviam sozinhos.

**Dispatch (`whatsapp.ts`).** `sendViaBridge` → `handleBridgeSendFailure` → mutation `internalDecideBridgeFailure` (veredito atômico `retry | failed | selfheal`; estado em `metadata.bridgeAttempts`, `bridgeRetry` visível durante o backoff, `selfHealAt`, `numberCheck`). Self-heal: no máximo UMA vez por mensagem (`selfHealAt` gravado na mesma mutation) e só se o contato tem vaga no orçamento de consultas; contato já marcado `not_on_whatsapp` falha direto, sem consulta (cobre o envio manual com aceite). Resposta do gateway em `internalApplyBridgeSelfHeal`: outra grafia do mesmo número (`isSpellingOfSameNumber`) sem opt-out em NENHUMA grafia → `applyCanonicalNumberToContact` (regra `canonicalContactPatch` da Nova conversa, audit + nota com telefone mascarado) e reagenda a MESMA mensagem uma vez; não existe → marcador `not_on_whatsapp` + falha; inconclusivo (gateway diz que ESTE número existe mas o envio deu `no LID`, telefone fora das grafias, checagem fora do ar) → falha sem marcador nem reescrita (`numberCheck` `inconclusive`/`unavailable`). Retries e reenvio pós-correção usam `rescheduleWhatsappDispatch` (`lib/whatsappDispatch.ts`): novo slot no cursor do canal e da conversa, mesmo pacing do envio original. `markDispatchFailedCore` é o corpo único de "falhou" (atividade, campanha, follow-up, repasse de boas-vindas, Telegram) e só roda na falha DEFINITIVA. Na Meta, `deliveryErrorCode` sozinho NÃO dispensa o aceite (códigos genéricos vêm com 5xx): só HTTP 4xx grava `deliveryPreSend`; 5xx/rede ficam sem classe. Cada nova falha apaga classe/código/pré-envio antigos (`markDispatchFailedCore`, reset da tradução). `bridgeRetry.nextAt` é o horário REAL agendado (pacing incluso).

**Validação do telefone canônico na raiz.** `checkBridgeNumber` descarta qualquer telefone que não esteja em `phoneLookupCandidates(perguntado)` e devolve `ok:false` (um mapa/cache de LID errado não reescreve contato nem manda para outra pessoa); todos os chamadores (Nova conversa, campanha, self-heal, boas-vindas, retry, ops) tratam `ok:false` como "não verificado" com o número do próprio destinatário.

**Marcador e portas (`lib/whatsappCheck.ts`).** `contacts.whatsappCheck {phone,status,checkedAt}` (aditivo): é INVALIDADO POR COMPARAÇÃO, não "limpo na edição": `not_on_whatsapp` vale para qualquer grafia BR do número (`phoneLookupCandidates`, a checagem pergunta as duas de uma vez; editar 13 ↔ 12 dígitos NÃO derruba) e `verified` só para os mesmos dígitos; a edição em `contacts.ts` só apaga o que deixou de valer (`markerSurvivesNumberChange`); mensagem recebida (`internalReceiveMessage`) limpa o `not_on_whatsapp`; só marca o número realmente checado (`contactNumberWasChecked`); `setWhatsappCheck` sempre regrava `checkedAt`. `contacts.whatsappLookup {phone,at,day,count}` + `reserveWhatsappLookup`: orçamento de consultas POR CONTATO (não por número: editar A → B → A não devolve nada; 10 min entre consultas, 3 por dia UTC), porta ÚNICA do self-heal, da pré-checagem das boas-vindas, do "Tentar novamente" e do op de reparo; o OCC no doc do contato serializa mensagens diferentes. Fora do orçamento, de propósito: Nova conversa SEM contato do número (ação autenticada de uma pessoa, uma consulta por clique; com contato passa pelo orçamento e pela guarda barata: marcador < 10 min responde do marcador, `fromMarker`, sem gateway) e o worker de campanha (uma consulta por destinatário distinto, já limitada pelo pacing da campanha). Nova conversa passa pelo orçamento quando o número JÁ tem contato (`internalReserveStartLookup`, `startFlow`: "conferir" + "iniciar" são uma interação; a 1ª reserva, se sobra vaga para duas, abre UMA consulta extra por 2 min, isenta só do espaçamento de 10 min e CONTADA no teto diário); sem vaga responde do marcador. O teto de 3 consultas por contato por dia UTC é, portanto, o máximo real, rajada inclusa. Número SEM contato fica fora (não há onde reservar): a ação exige membro autenticado com `inbox:reply` e é uma consulta por clique/chamada. `contacts.whatsappFails {phone,count,at}`: respostas REAIS `no LID found` do gateway SEGUIDAS (a falha recusada pelo próprio gate não conta; contagem em `internalDecideBridgeFailure`) quando nada pôde ser marcado (checagem indisponível/inconclusiva). EXATO nos dígitos (um `no LID` é daquele JID; o marcador `not_on_whatsapp` é que vale nas duas grafias porque a checagem perguntou ambas). A partir de 2 (`NOT_FOUND_FAILS_BLOCK`) o gate dos automáticos para e o manual pede o mesmo aceite; o self-heal CONTINUA consultando (com vaga no orçamento do contato), pois é o que pode consertar o contato. Zera com mensagem recebida, envio aceito pelo gateway (`internalMarkDispatched`), qualquer edição do número e correção do número (`applyCanonicalNumberToContact`). "Existe" para o MESMO número que já deu `no LID` seguido é INCONCLUSIVO em todos os caminhos (self-heal, retry, campanha, boas-vindas, Nova conversa): `setWhatsappCheck(…, "verified")` não grava nem zera enquanto o contador for > 0, e o retry recusa com `check_unavailable`; campanha e boas-vindas então esbarram no gate (falha visível "…envio automático bloqueado"), e Nova conversa abre a conversa (ação humana) cuja 1ª mensagem também para no gate — o envio manual com aceite é o caminho. Marcador e contador só valem para conversa que sai pelo BRIDGE (`conversationIsBridge`): envio pela Meta não é bloqueado nem reseta nada. "Tentar novamente" em contato bloqueado exige checagem POSITIVA antes (a confirmação zera o contador e libera o gate; o retry nunca carimba o aceite) e recusa com `check_unavailable` sem ela. Escrito por: self-heal, boas-vindas, Nova conversa e campanha (`verified`/`not_on_whatsapp`), "Tentar novamente", op de reparo.

**Aceite só de pessoa:** `notOnWhatsappAck` e `maybeDeliveredAck` são recusados no servidor quando quem age é membro `ai` (chave de API de IA, Copiloto; `HUMAN_ACK_REQUIRED_ERROR`). **Gate dos automáticos** = `dispatchMessage` (IA, follow-up, agendada, boas-vindas e campanha passam por ele): contato marcado para o número atual e sem `metadata.notOnWhatsappAck` → falha visível (`recipient_not_found`, `deliveryPreSend`), sem rede. Alternativa descartada: cinco cópias; o custo é a falha ser registrada no dispatch. **Envio manual** (`sendMessage`, `forwardMessage`, `internalSendMessageCore` → REST `/conversations/send` e MCP `crm_send_message`): "avisar, não travar" — `ConvexError("NOT_ON_WHATSAPP: …")` (REST 409 `{notOnWhatsapp:true}`) até vir `notOnWhatsappAck: true`; o aceite grava `metadata.notOnWhatsappAck {by,at,via}` e auditoria `high`. Copiloto (`copilotAttendantTools`) e Telegram nunca definem o aceite e mostram texto humano, sem o prefixo técnico.

**Boas-vindas do site.** `internalRunInboundLeadWelcome` (action chamada pela rota, que responde de forma síncrona com `welcomeQueued`/`welcomeSkippedReason`; a consulta ao gateway tem 4 s) → mutation `internalWelcomePrecheckPlan` (mesma cadeia de guardas `welcomeGuards` da mutation final; pula com marcador `verified` < 30 dias ou `not_on_whatsapp` válido; reserva a consulta no orçamento do contato) → `internalSendInboundLeadWelcome` com `numberCheck` + `checkedPhone` (a pré-checagem já gastou a vaga de 10 min do contato: uma boas-vindas que passou por ela NÃO faz self-heal depois, e termina em no máximo UM envio e UM repasse) (resposta cujo número já mudou é ignorada): grafia do mesmo número → persiste e envia a ela; sem WhatsApp (ou marcador válido) → marcador + repasse `Número sem WhatsApp — boas-vindas não enviadas` (PT-BR, sem texto do gateway), `welcomeSkippedReason: "numero_sem_whatsapp"`; indisponível/inconclusivo → envia como antes. No bridge a mutation NÃO reescreve `whatsappNumber` (só preenche se vazio); Meta mantém o comportamento antigo. Opt-out olha as duas grafias BR. `contacts.internalFindOrCreateContact` acha o contato por ambas as grafias (`findContactsByPhoneCandidates`), sem duplicar.

**Tentar novamente.** `messageRetry.retryFailedMessage({messageId, maybeDeliveredAck?})` (action pública) → `internalPrepareRetry` (MUTATION que reserva a consulta: `metadata.numberChecks` ≤ 3 e 10 min por mensagem + orçamento do contato; marcador recente recusa sem consultar) → `checkBridgeNumber` → `internalCommitRetry` (re-roda as guardas, aplica o veredito, zera o erro, `scheduleOutboundDispatch`, atividade + audit). Guardas: RBAC `inbox:reply`; teto 3 reenvios manuais; recusa mensagem de campanha (`campaignRecipients.by_message` / `metadata.campaign`: a campanha reenvia sozinha); opt-out nas duas grafias, com contato sem DDI normalizado; `needsDeliveredAck` (lista positiva: `recipient_not_found`/`transient`/`rate_limited`, `deliveryPreSend`, código definitivo da Meta; o resto, inclusive sem classe, exige o aceite `maybe_delivered`). `selfHealAt` e `bridgeAttempts` NÃO são zerados. Resultado `{ok:true,correctedNumber}` ou `{ok:false,reason,message,retryAfter?}`; a UI lê `getMessages[].deliveryRetry` (`canRetry`, `requiresCheck`, `requiresDeliveredAck`, `numberChecks`, `retryAfter` — "um reenvio agora seria recusado até este instante", só presente com `requiresCheck` —, `autoRetrying`, `autoRetryNextAt`). Se o gateway diz que ESTE mesmo número existe depois de um `no LID found`, o retry recusa (`check_unavailable`), igual ao self-heal (`inconclusive`).

**Ops.** `opsBridgeNumbers.internalRepairNoLidNumbers({organizationId, sinceMs?, dryRun=true, lookup?, cursor?, pageSize?})`: o dry run só LISTA candidatos (sem consultar o gateway) salvo `lookup:true`; fora do dry run consulta (~1 s entre contatos), pula contato já marcado/verificado para o número atual, corrige `whatsappNumber` ou marca, nunca reenvia, uma auditoria por página; cada consulta reserva o orçamento do contato (`skipped_budget` quando não há vaga) e a página PARA no primeiro `check_failed` (sem reagendar); dedup só dentro da página, entre páginas quem limita é o orçamento. `opsMigration.internalRedispatchStuckOutbound` pula mensagem com `bridgeRetry`/`selfHealAt` só dentro de uma janela de graça (30/15 min); passada ela, o estado é considerado morto e a mensagem é redispatchada.

**Fora de escopo / observado:** JID de grupo de 18 dígitos (`1203…`) já foi enviado como telefone (18/09); não corrigido aqui. Não coberto: o limbo "action morreu entre o envio e o registro" (segue com `internalRedispatchStuckOutbound`).

### Nota de voz do navegador: /convert e reserva (nov/2026, áudio no iPhone)

O gravador do inbox sobe `audio/ogg` (Firefox), `audio/webm` (Chrome/Edge) ou `audio/mp4` com `.m4a` (Safari, inclusive o app instalado no iPhone). No `dispatchViaBridge`, nota de voz (`contentType:"audio"`) que não é ogg passa pelo `/convert?target=ogg-opus` do serviço Whisper (VPS, fora do repo). O arquivo vai no form com o nome de `voiceNoteConvertFilename` (`lib/bridgeSend.ts`): `voice-note.m4a` (ou `.aac`) SÓ para mp4/m4a/aac, como dica do contêiner de entrada; webm e o resto seguem `voice-note` sem extensão, que é o caminho do Chrome já em uso (mudar exigiria validar no serviço). Nunca se verificou no serviço se ele aceita mp4/AAC: é a primeira coisa a olhar se o iPhone falhar.

**Reserva (`planBridgeAudioSend`, puro):** ogg sai como está por `/chat/send/audio`; convertido sai por `/chat/send/audio` como `audio/ogg; codecs=opus`; sem conversão (serviço sem env ou com erro) o original sai como DOCUMENTO por `/chat/send/document`, com nome cuja extensão segue o tipo REAL (`audio/mp4` → `.m4a`, mesmo que o arquivo antigo do iPhone se chame `.webm`), e a mensagem ganha `metadata.dispatchNote` ("Nota de voz enviada como arquivo de áudio…"). O endpoint de áudio nunca recebe `data:audio/mp4`/`data:audio/webm` (o wuzapi espera ogg ali). Escolhemos documento em vez de falhar porque o endpoint de documento já é o de todo PDF/Office do inbox, coberto por `bridgeDispatch.test.ts`, e o contato ainda recebe um áudio tocável. Testes: `voiceNoteDispatch.test.ts`, `bridgeMedia.test.ts`.

### Resposta em áudio da IA: PTT, duração e waveform (onboarding v2, P4.1)

A resposta em áudio do atendente (`docs/architecture/ai-attendant.md`, seção P4.1) chega ao dispatch como mensagem `contentType:"audio"` com anexo `audio/ogg` já convertido (o `/convert` roda na geração, pela mesma porta `lib/voiceNoteConvert.ts` que o dispatch usa para a gravação do navegador) e `metadata.voiceNote = {seconds, waveform}` calculados do PCM do TTS. No bridge, `planBridgeAudioSend({..., voiceNote})` devolve `voiceFields` e `buildBridgeMediaSendRequest` acrescenta ao corpo do `/chat/send/audio`: `PTT: true`, `MimeType: "audio/ogg; codecs=opus"`, `Seconds` (inteiro, 1–3600) e `Waveform` (string base64 dos 64 bytes 0–100; `[]byte` do Go em JSON). Os nomes vêm do handler `SendAudio` do wuzapi upstream (`ptt`/`mimetype` com tag JSON em minúsculas; o decoder do Go casa sem diferenciar maiúsculas); a versão que roda na VPS gerenciada NÃO foi conferida, e um gateway mais antigo ignora campos desconhecidos. O data-URI sai `data:audio/ogg;base64,...` (o tipo do arquivo é `audio/ogg` sem `codecs`, o formato mais seguro apontado pelo spike) e o mime explícito vai no campo `MimeType`. Waveform inválida é descartada e só `Seconds` segue; `voiceNote` inválido não manda campo nenhum. Áudio de humano (sem `metadata.voiceNote`) continua com o corpo de antes, sem campo novo; documento (sem conversão) nunca leva esses campos. Áudio não leva legenda: o texto falado fica só no histórico.

**Cloud API (Meta).** O ogg sai pela porta de sempre como `type:"audio"` com `link` (sem legenda, sem campos do bridge). Não mandamos `voice:true` nem conferimos se o WhatsApp oficial o mostra como mensagem de voz (com ondinha) ou como arquivo de áudio: item do roteiro de teste vivo.

Validação viva pendente (roteiro do spike, V3): chega como mensagem de voz com ondinha e duração no Android e no iPhone; testes `voiceNoteDispatch.test.ts`, `lib/tts.test.ts`.
