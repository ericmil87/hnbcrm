# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev              # Start frontend (Vite) + backend (Convex) in parallel
npm run dev:frontend     # Start only Vite dev server
npm run dev:backend      # Start only Convex dev server
npm run build            # Build frontend (vite build)
npm run convert-images   # Convert PNG images to WebP format
npm run lint             # Full check: tsc (convex + app) → convex dev --once → vite build
npx convex dev --once    # Push schema/functions to Convex without watching
```

Tests: `npm run test` (vitest + convex-test; `*.test.ts` em `convex/`). Seed data is available via `convex/seed.ts`.

## Architecture

Multi-tenant CRM with human-AI team collaboration. Convex backend, React + TailwindCSS frontend.

**Multi-tenancy:** Every table has `organizationId`. All queries must be scoped to the user's org.

**Auth flow:** `requireAuth(ctx, organizationId)` from `convex/lib/auth.ts` handles auth + org membership. Returns the team member. `requirePermission(ctx, organizationId, category, level)` extends this with granular RBAC checks. A few functions without org context (e.g. `getUserOrganizations`) still use `getAuthUserId` directly.

**Permissions (RBAC):** 10 permission categories (leads, contacts, inbox, tasks, reports, team, settings, auditLogs, apiKeys, campaigns) with hierarchical levels. Defined in `convex/lib/permissions.ts`. Each role (admin, manager, agent, ai) has sensible defaults; admins can override per-member. Frontend uses `usePermissions(organizationId)` hook and `<PermissionGate>` component.

**Invite flow:** Admins invite humans via `inviteHumanMember` action (creates auth account with bcrypt-hashed temp password). New users must change password on first login (`mustChangePassword` flag). Users auto-linked to org via `afterUserCreatedOrUpdated` auth callback.

**Side effects in mutations:** Most mutations insert into `activities` + `auditLogs` and trigger webhooks via `ctx.scheduler.runAfter(0, internal.nodeActions.triggerWebhooks, ...)`.

**Email/Notifications:** `@convex-dev/resend` component for email delivery. Central dispatch via `convex/email.ts` — all events go through `internal.email.dispatchNotification`. Templates in `convex/emailTemplates.ts` (PT-BR). Per-member preferences in `notificationPreferences` table (opt-out model — no row means all enabled). Convex components registered in `convex/convex.config.ts`. **Email env vars:** `RESEND_API_KEY`, `APP_URL`, `RESEND_FROM_EMAIL` (default: `HNBCRM <noreply@mail.hnbcrm.com>`), `RESEND_WEBHOOK_SECRET`. Domain: `mail.hnbcrm.com` (subdomain to avoid Gmail MX conflict).

**HTTP API:** `convex/router.ts` has RESTful endpoints at `/api/v1/` authenticated via `X-API-Key` header. API keys resolve permissions from key → team member → role defaults. **RBAC enforçado em TODAS as rotas (v0.47):** mapa único `ROUTE_PERMISSIONS` (`"MÉTODO /rota"` → categoria+nível espelhando o `requirePermission` da função app equivalente, ou `"authenticated"` p/ rotas self-scoped) + `requireRoutePermission` logo após `authenticateApiKey` em cada handler; fail-closed (rota sem entrada = 403 "Permissão insuficiente"); teste de build `routerPermissions.test.ts` garante completude e gate em cada handler. Rate limit por key: 300 req/min (fixed window em `apiKeys.updateLastUsed`, 429). Routes wired in `convex/http.ts`.

**WhatsApp channel:** Per-organization channel configs (`convex/channelConfigs.ts`, `channelConfigs` table) with `provider: "meta" | "bridge"` — two transports on the same `whatsapp` channel. `meta` = official WhatsApp Cloud API (Graph API, 24h service window, message templates); ingress at `GET/POST /webhooks/whatsapp` (`convex/whatsapp.ts`). `bridge` = self-hosted wuzapi gateway (WhatsApp Web protocol via whatsmeow, QR pairing, no 24h window, no templates); ingress at `POST /webhooks/bridge` verified by HMAC-SHA256 via env `WA_BRIDGE_HMAC_SECRET` (`convex/bridge.ts`). Managed provisioning: envs `WA_BRIDGE_DEFAULT_URL` + `WA_BRIDGE_ADMIN_TOKEN` (both set = "Servidor HNBCRM" default in the provisioning form — user only types a display name; admin token never leaves the server; advanced users can still point to their own gateway). Bridge is opt-in per org and carries a permanent-ban risk (unofficial protocol, violates WhatsApp ToS). Key files: `convex/bridge.ts`, `convex/lib/bridgeParse.ts` (pure parser), `convex/lib/bridgeSend.ts` (text), `convex/lib/bridgeMedia.ts` (media), `convex/lib/bridgeSession.ts` (QR/status/provisioning). Outbound dispatch in `convex/whatsapp.ts` branches by provider (voice notes are transcoded to ogg/opus via the Whisper service's `/convert`). Typing presence and delivery/read receipts flow both ways (`sendTypingState`, `markConversationRead`, `ChatPresence`/`ReadReceipt` webhook events). UI in `src/components/settings/ChannelsSection.tsx` (+ `ChannelHealthPanel` with 7-day delivery stats).

**Bridge — mensagem do aparelho, histórico e exclusividade do número (v0.56):** três coisas que faltavam para o inbox bater com a conversa real. (1) **`fromMe` entra como `outbound`:** o parser descartava todo `Info.IsFromMe` para evitar o eco do próprio CRM, mas o WhatsApp multi-device usa o MESMO evento para o eco e para o que um humano digita no app do celular — descartar os dois fazia a conversa divergir (e o atendente IA lia um histórico incompleto). Agora vai para `conversations.internalReceiveDeviceMessage` (`metadata.via:"device"`, sem `senderId`, NÃO mexe em `lastInboundAt`/`unreadCount`, NÃO enfileira a IA nem transcrição/visão; o eco morre na idempotência de `externalId`). O telefone sai do `Chat` (o `Sender` somos nós) e o `PushName` é descartado (é o nosso — renomearia o contato). Reação nossa e grupo seguem ignorados. (2) **Histórico do aparelho, POR NÚMERO, opt-in default OFF** (`channelConfigs.bridgeHistoryEnabled/Limit/Days`, 100 msgs/conversa e 7 dias): o wuzapi guarda as mensagens numa tabela própria quando o instance tem `history > 0`, e cada linha traz o evento whatsmeow ORIGINAL — a importação reusa `parseBridgeEvent` e o ingest inteiros, então re-sincronizar não duplica. `lib/bridgeHistory.ts` (puro) + `bridge.setBridgeHistoryConfig`/`syncBridgeHistory`/`internalImportBridgeHistory`; UI no card do número. **Importa só `fromMe`, de propósito:** a recebida sempre chegou pelo webhook, e reinjetá-la passaria por `internalReceiveMessage`, que enfileira o atendente — numa org em autopilot a IA responderia no WhatsApp a uma pergunta de dias atrás. **Pegadinhas do wuzapi medidas contra o gateway real** (fixtures nos testes): o campo é `data_json` (snake_case, o alias `datajson` só existe no SELECT interno); a coluna `timestamp` da linha é o instante da GRAVAÇÃO, não o da mensagem (num HistorySync as 50 linhas vieram com o mesmo carimbo sendo de meses atrás — a hora real sai de `data_json.Info.Timestamp`); conversa sem histórico devolve `{"code":200,"data":null}`, que tratado como erro fazia TODA a varredura falhar. O HistorySync sob demanda é best-effort de verdade (pedimos 100 e vieram 50, todas antigas). (3) **Um número = uma conta:** `channelConfigs.bridgePhone` (dígitos) + índice `by_bridge_phone` DEPLOYMENT-WIDE. O mesmo número pareado em duas orgs faz cada mensagem do contato ser ingerida nas DUAS — vazamento entre inquilinos, não só ruído. Ao ficar "connected", `claimBridgePhone` (dentro de `internalRecordHealthCheck`, MESMA transação, então não há janela com os dois ativos) desativa os outros canais com aquele número, audita na org DESLOCADA (severity `high`), pausa as campanhas dela e agenda `internalLogoutBridgeInstance` (`POST /session/logout` com o token da própria instância — desvincula o aparelho; `/session/disconnect` só derruba o socket e não serve). `deleteChannelConfig` também agenda o logout: era ELE que criava instâncias órfãs logadas para sempre. **Pegadinha decisiva:** `GET /session/status` devolve `jid: ""` mesmo logado (medido em 3 instâncias) — por isso `displayPhoneNumber` nunca era preenchido em canal bridge; o número sai de `GET /admin/users` (`phoneFromAdminUsers`), disponível só no gateway GERENCIADO, então em self-hosted a chave fica vazia e a regra não dispara. Aviso genérico no modal do QR antes de escanear (o número só é conhecido depois) + banner nomeando as contas deslocadas, sem auto-close. **(4) Correção de fundo:** `buildBridgeConnectRequest` mandava `Subscribe: ["Message"]` por padrão e o `Connect()` do wuzapi faz `UPDATE users SET events=$1` — todo reconnect REESCREVIA a assinatura feita no provisionamento, e por isso os recibos de entrega/leitura estavam mortos desde 2026-08-07 (todos os outbound travados em `sent`). **Defesas da mídia inbound (v0.53):** três achados colaterais do plano de visão, corrigidos. (1) **Allowlist + quota na porta de entrada:** `internalSaveInboundAttachment` (`convex/whatsapp.ts`, usada pelos DOIS transportes) passou a aplicar as mesmas defesas do upload humano — `checkInboundMediaMimeType` (allowlist do upload + extras que só chegam pelo WhatsApp: vídeo, codecs de celular, zip, slides) e `checkInboundMediaQuota`. Diferença deliberada: **nada lança** — quem manda o anexo é o contato, e derrubar a mensagem dele perderia o texto no inbox; recusa devolve `{ ok:false, reason }`, o ingest marca `metadata.mediaSkipped` e o blob já armazenado é apagado na hora (não há cron de limpeza de órfão). O teto por arquivo do plano NÃO se aplica — quem limita é o `MAX_MEDIA_BYTES` de 25 MB do ingest. (2) **`MediaKey` fora do banco:** `metadata.bridgeMedia` guardava o descriptor whatsmeow inteiro, com a chave que decifra o blob na CDN, para sempre. Agora só `sanitizeBridgeMediaMeta` (kind/mimeType/filename/fileLength) é persistido, e `stripMediaKeyMaterial` varre o metadata inteiro antes do banco como rede de segurança (pega até o `metadata.raw` de tipo desconhecido). Backfill: `internal.bridge.internalBackfillBridgeMediaKeys`. (3) **Blob compartilhado:** `forwardMessage` duplica a linha de `files` com o mesmo `storageId` (de propósito — `files.messageId` é 1:1), e qualquer exclusão apagava o blob deixando a outra cópia quebrada. `lib/fileRefs.ts` condiciona só o `ctx.storage.delete` a não haver outra linha com aquele `storageId` (índice `by_storage_id`); na dúvida o blob FICA. **Correção da espera de mídia (v0.53):** `hasMediaAwaitingEnrichment` deixou de esperar por `metadata.mediaPending`. O nome engana: o download do bridge é SÍNCRONO dentro da action de ingest e a mensagem só é gravada depois dele, então o campo nunca significa "os bytes estão a caminho" — só é escrito em caminhos de FALHA (mídia grande demais, erro de download, anexo recusado), o Meta nem o escreve, e o inbox o lê como `hasMediaProblem`. **Mídia que a IA não consegue ler (v0.53):** o PDF continua fora do alcance da visão (nenhum modelo da cadeia aceita PDF como `image_url`, e não há como rasterizar numa action do Convex), mas mandar comprovante em PDF é comportamento comum de cliente — e até aqui a IA via só `"comprovante-pix.pdf"` no histórico e respondia como se fosse uma mensagem de texto. `historyTextOf` ganhou o ramo de `contentType: "file"`: `[arquivo recebido: <nome> — não consigo abrir arquivos]`, `[arquivo recebido — não consigo abrir arquivos]` quando o parser só tem placeholder, `[vídeo recebido — não consigo assistir a vídeos]` (mesmo contentType, mídia diferente) e `[arquivo enviado]` no outbound. **Não é gated por `visionEnabled`** — a IA nunca conseguiu abrir PDF, com ou sem visão. **REGRA 8** no prompt manda dizer que não abriu, confirmar pelo nome e pedir um print (que a visão lê), e reitera o D13 para o caso de o nome parecer comprovante.

**Visão: imagem descartada no caminho (fix 2026-09-14):** incidente real na org Aos Filhos da Terra — 3 comprovantes gravados como "Nenhuma imagem foi enviada" e o atendente pediu reenvio às clientes. Cadeia de causas, medida: (1) o body do OpenRouter com `allow_fallbacks:false` só tenta o provedor PRIMÁRIO — DeepInfra dava 429 para `glm-5.3-flash` e `kimi-k2.7-code` enquanto GMICloud/Fireworks/StreamLake (aceitos sob `data_collection:"deny"`) respondiam; (2) a cadeia desceu até um provedor do kimi que DESCARTOU a imagem e respondeu 200 com 425 tokens de entrada (= prompt sozinho); (3) a frase "nenhuma imagem" não era vazia, então passava como descrição. Correções em `convex/vision.ts`: a visão manda `allow_fallbacks:true` no OpenRouter (mantém `data_collection:"deny"` + `require_parameters`; o `OPENROUTER_ZDR_PROVIDER_BODY` do atendente/copiloto NÃO mudou); duas camadas contra imagem descartada, ambas = próximo elo — campo `imagem_recebida` no JSON do prompt e piso de tokens `VISION_TEXT_ONLY_PROMPT_TOKENS`/`visionImageDropped` no registry (prompt sem imagem medido por modelo; **mudou o prompt, re-meça** — o teste de tamanho do prompt quebra de propósito); `metadata.vision.upstream` (provedor que atendeu) + `attempts` (uma linha por elo que falhou); leitura `failed` apaga o espelho `imageDescription`. **Reprocessar uma imagem mal lida:** `vision:internalSetVisionResult {messageId, status:"failed", error}` → `vision:autoDescribe {messageId}`. **Achado colateral:** a rota OpenCode Go devolve 400 `Request is missing x-opencode-session` desde pelo menos 08/09 em TODOS os produtos — a doc do Go restringe o uso a tráfego de agente de código, então não é caso de só mandar o header.

**Config de IA por produto (v0.52):** cada produto de IA (`copilot` | `attendant` | `vision`) escolhe a PRÓPRIA rota, e a visão também o próprio modelo — em `organizations.settings.aiConfig.providerConfig.products` (`{ order?, model? }` por produto; ausente = herda). ## Convex Rules (mandatory)

Rules from `.cursor/rules/convex_rules.mdc` and `.claude/convex-agent-plugins/rules/`:

- **Always** use new function syntax: `query({ args: {}, returns: v.null(), handler: async (ctx, args) => {} })`
- **Always** include `args` and `returns` validators on every function
- **Never** use `.filter()` on queries — use `.withIndex()` instead
- **Never** use `Date.now()` inside queries — breaks reactivity
- **Never** schedule `api.*` functions — only schedule `internal.*` functions
- Use `internalQuery`/`internalMutation`/`internalAction` for non-public functions
- Actions using Node.js APIs must include `"use node";` directive and be in a separate file
- Use `ctx.db.patch` for partial updates, `ctx.db.replace` for full replacement
- Index naming: `by_<field>` or `by_<field1>_and_<field2>`
- Use `"skip"` pattern: pass `"skip"` to `useQuery` when args aren't ready
- Keep query/mutation handlers thin — extract business logic into plain TypeScript functions
- Use cursor-based pagination (`paginationOptsValidator`) for large datasets
