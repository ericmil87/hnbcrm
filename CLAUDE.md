## Architecture

Multi-tenant CRM with human-AI team collaboration. Convex backend, React + TailwindCSS frontend.

**Multi-tenancy:** Every table has `organizationId`. All queries must be scoped to the user's org.

**Auth flow:** `requireAuth(ctx, organizationId)` from `convex/lib/auth.ts` handles auth + org membership. Returns the team member. `requirePermission(ctx, organizationId, category, level)` extends this with granular RBAC checks. A few functions without org context (e.g. `getUserOrganizations`) still use `getAuthUserId` directly.

**Permissions (RBAC):** 10 permission categories (leads, contacts, inbox, tasks, reports, team, settings, auditLogs, apiKeys, campaigns) with hierarchical levels. Defined in `convex/lib/permissions.ts`. Each role (admin, manager, agent, ai) has sensible defaults; admins can override per-member. Frontend uses `usePermissions(organizationId)` hook and `<PermissionGate>` component.

**Invite flow:** Admins invite humans via `inviteHumanMember` action (creates auth account with bcrypt-hashed temp password). New users must change password on first login (`mustChangePassword` flag). **Não existe mais auto-link por e-mail no cadastro** (v0.61) — ver "Multi-org" abaixo.

**Multi-org N:N usuário↔empresa (v0.61):** 1 usuário em N orgs, 1 org com N membros (linha `teamMembers` por par org+user). (1) **Remover corta o acesso:** `removeTeamMember` grava `removedAt`/`removedBy` (+ `status:"inactive"`); `isMembershipRevoked` = `removedAt` OU `inactive` legado (nada além da remoção grava `inactive`, e `updateTeamMemberStatus` só aceita `active`/`busy` — ninguém se reativa sozinho). `getActiveMembership` em `lib/auth.ts` é a base de `requireAuth`/`requirePermission`, dos lookups manuais, de `getUserOrganizations` e de `getByKeyHash` (API key de removido ou cross-org não autentica; `insertApiKey` valida a org do membro). Reconvidar REATIVA a mesma linha; todo caminho que põe IA em `active` limpa `removedAt`. Atribuição (lead/tarefa/repasse/evento) passa por `assertAssignableMember` — removido não recebe atribuição NOVA (quem já era responsável segue válido na re-edição). `getTeamMembers` devolve `removed`/`pending` (pendente = humano sem `userId`, legado; não conta na guarda de último admin). (2) **Convite:** `createTeamMember` só cria IA; humano sempre por `inviteHumanMember` → `{teamMemberId,isNewUser,existingUser,reactivated,pendingPasswordChange,tempPassword?,emailSent}` — conta existente é vinculada sem tocar na senha e recebe e-mail `addedToOrg`; aplica `ROLE_RANK`. O auto-link em `afterUserCreatedOrUpdated` foi REMOVIDO: o cadastro não verifica e-mail, então qualquer um que se cadastrasse primeiro com o e-mail de um membro pré-criado entrava na org (até como admin); pendente legado é adotado quando o admin reconvida. (3) **E-mail sem caixa:** lookup de conta acha qualquer variante (forma exata vence se houver duas); login normaliza via `withCanonicalEmail`; cadastro com variante de conta existente é recusado. Backfill `authHelpers:internalNormalizeLegacyEmails {table, dryRun(default true), cursor}` só reporta colisões. (4) **Senha temporária é da CONTA:** `teamMembers.getMustChangePassword` (sem org) trava o app antes de tudo em qualquer org; convite de conta com senha pendente herda o flag; trocar limpa todos os membros. (5) **Onboarding por org:** `getOnboardingProgress.shouldShowWizard` só para admin de org sem `onboardingMeta.wizardCompletedAt`; `setupPipelineFromWizard` recusa após conclusão ou com leads (ele apaga boards). (6) **Front:** `src/components/org/OrgSwitcher.tsx` (modal: lista, "Nova organização", Sair — também no header/menu "Mais" do mobile); `key={orgId}` no AppShell e `src/lib/orgSwitch.ts` limpam `?task=/lead=/conversation=/handoff=` na troca; deep-link de entidade de OUTRA org resolve por `organizations.resolveEntityOrg` e troca de org (ou "não encontramos"); queries de detalhe devolvem null para não-membro; ErrorBoundary reseta por rota; signOut limpa `hnbcrm.selectedOrgId` e toasts; aviso "Você foi adicionado" só com `invited:true` de `getUserOrganizations`. (7) `updateOrganization`/`completeWizard` fazem MERGE de `settings` (antes o Salvar do perfil apagava `optOutKeywords`/`campaignDefaults`). Testes: `convex/multiOrg.test.ts`, `src/lib/orgSwitch.test.ts`, `src/lib/teamMembers.test.ts`.

**Side effects in mutations:** Most mutations insert into `activities` + `auditLogs` and trigger webhooks via `ctx.scheduler.runAfter(0, internal.nodeActions.triggerWebhooks, ...)`.

**Email/Notifications:** `@convex-dev/resend` component for email delivery. Central dispatch via `convex/email.ts` — all events go through `internal.email.dispatchNotification`. Templates in `convex/emailTemplates.ts` (PT-BR). Per-member preferences in `notificationPreferences` table (opt-out model — no row means all enabled). Convex components registered in `convex/convex.config.ts`. **Email env vars:** `RESEND_API_KEY`, `APP_URL` (default `https://hnbcrm.com` via `lib/appUrl.ts` — fonte ÚNICA de link em e-mail), `RESEND_FROM_EMAIL` (default: `HNBCRM <noreply@mail.hnbcrm.com>`), `RESEND_WEBHOOK_SECRET`, `RESEND_TEST_MODE` (só `"true"` liga o sandbox). Domain: `mail.hnbcrm.com` (subdomain to avoid Gmail MX conflict).

**E-mail transacional que de fato sai (v0.59):** o componente tem `testMode: true` por DEFAULT e nesse modo LANÇA para todo destinatário que não seja `@resend.dev`; `email.ts` nunca desligou, então nenhum e-mail saiu por meses — e como 14 dos 15 call sites agendam o envio, o erro só existia no log (medido: 135 falhas/dia, todas do digest; o sino in-app funcionava, daí ninguém notar). Agora envio real é o padrão (`resendTestMode()`), e `emailConfig.test.ts` quebra se o default voltar. **Porta de saída única `sendTransactionalEmail`** (em `email.ts`): valida o endereço (`lib/emailAddress.ts` — barra o lixo já gravado tipo `"toni"` e domínios de seed como `demo.com`, que é domínio REAL de terceiro), checa `emailSuppressions` e **nunca lança** (e-mail é efeito colateral; devolve `false`). `dispatchNotification` devolve boolean e barra: membro de OUTRA org (defesa multi-tenant — `leads.assignLead` aceitava responsável de outra org e a notificação levaria o título do lead para fora; fechado nos dois `assignLead`), membro sem `userId` (seed/importado não tem como abrir o link) e eventType sem template (`buildTemplate` agora é fail-closed; antes mandava um e-mail vazio "Evento: x"). **Supressão:** `emailSuppressions` é DEPLOYMENT-WIDE de propósito (a reputação do domínio remetente é uma só); `handleEmailEvent` grava em hard bounce (`bounce.type === "Permanent"`; transitório não) e em denúncia de spam. **Convite:** `inviteHumanMember` valida o formato ANTES de gravar e devolve `emailSent` — action não é transacional, e o throw do e-mail impedia o `return` com a senha temporária (que só existia em memória), deixando um membro-zumbi que nem dava para reconvidar. **Digest** só vai para quem tem conta e pula dia zerado. **Pegadinhas:** "Success" diário no painel do Resend NÃO provava que o envio funcionava — era o digest indo para um membro de teste `@resend.dev`, o único tipo de endereço que o `testMode` deixa passar; a verdade está em `npx convex data emails --component resend` e nas falhas de `_scheduled_functions`. O webhook do Resend é por CONTA: evento de e-mail de outro projeto da mesma conta chega aqui e o componente descarta em silêncio (`Email not found for resendId`); os testes NÃO registram o componente (`resend.sendEmail` lança por componente ausente — é o que exercita o "nunca lança"), logo agendamento se verifica em `_scheduled_functions`, sem drenar a fila. Entrada de formulário público sai escapada em `formSubmission`/`formConfirmation`. Pendências conhecidas: flag `newMessage` sem emissor; 7 tipos in-app (`ai_draft_pending`, `campaign_*`, `group_joined|mention|opportunity|digest`) têm preferência na tela e nenhum e-mail; `formSubmission` sem flag de opt-out; usuário JÁ existente convidado para outra org não recebe e-mail nenhum.

**Recuperar senha + boas-vindas (v0.59):** não existia reset de senha — `auth.ts` usava `Password` puro. Agora `Password({ reset: passwordResetProvider })` (`convex/passwordReset.ts`): código numérico de 8 dígitos (rejection sampling, sem viés de módulo), validade de 15 min (`lib/passwordResetConfig.ts` — o default do Convex Auth é 24 h), dois passos no cliente: `signIn("password", {email, flow:"reset"})` → `{email, code, newPassword, flow:"reset-verification"}` (troca E autentica; senha ≥ 8). **O `sendVerificationRequest` recebe um ctx de action REAL como 2º argumento** (medido em `@convex-dev/auth` `signIn.js:78-97`; o tipo publicado declara só 1 parâmetro, daí o cast pontual), então o código sai por `ctx.runMutation(internal.authEmails.sendPasswordResetCode)` e pela MESMA porta `sendTransactionalEmail` — sem `AUTH_RESEND_KEY`, sem segundo canal, herdando supressão e validação. `convex/authEmails.ts` também tem `sendWelcomeEmail`, agendado por `organizations.createOrganization`; os dois ficam FORA de `notificationPreferences` (segurança da conta / primeiro contato) e nunca logam código nem endereço inteiro. **Teto de pedidos:** `authEmailThrottle` (5/h por endereço normalizado, janela fixa) — o flow `reset` é público e o Convex Auth só limita tentativa de CÓDIGO, não PEDIDO; sem isto o formulário vira canhão de e-mail contra terceiros usando o nosso domínio. **Anti-enumeração é no CLIENTE:** o provider lança `InvalidAccountId` para e-mail sem conta e não há como suprimir sem reimplementar o flow; `src/components/auth/ForgotPasswordForm.tsx` engole todo erro que não seja rede/rate-limit e avança com a mesma mensagem neutra. Hash de conta convidada (`lucia.Scrypt` em `inviteHumanMember`) é o mesmo do provider, então reset funciona para convidados sem migração. **`mustChangePassword` não é limpo pelo reset** (o Convex Auth não tem callback pós-reset): a tela chama `teamMembers.clearMustChangePasswordAfterReset` (só mexe nos membros do PRÓPRIO usuário; best-effort). Testes: `authEmails.test.ts`, `emailConfig.test.ts`.

**HTTP API:** `convex/router.ts` has RESTful endpoints at `/api/v1/` authenticated via `X-API-Key` header. API keys resolve permissions from key → team member → role defaults. **RBAC enforçado em TODAS as rotas (v0.47):** mapa único `ROUTE_PERMISSIONS` (`"MÉTODO /rota"` → categoria+nível espelhando o `requirePermission` da função app equivalente, ou `"authenticated"` p/ rotas self-scoped) + `requireRoutePermission` logo após `authenticateApiKey` em cada handler; fail-closed (rota sem entrada = 403 "Permissão insuficiente"); teste de build `routerPermissions.test.ts` garante completude e gate em cada handler. Rate limit por key: 300 req/min (fixed window em `apiKeys.updateLastUsed`, 429). Routes wired in `convex/http.ts`.

**WhatsApp channel:** Per-organization channel configs (`convex/channelConfigs.ts`, `channelConfigs` table) with `provider: "meta" | "bridge"` — two transports on the same `whatsapp` channel. `meta` = official WhatsApp Cloud API (Graph API, 24h service window, message templates); ingress at `GET/POST /webhooks/whatsapp` (`convex/whatsapp.ts`). `bridge` = self-hosted wuzapi gateway (WhatsApp Web protocol via whatsmeow, QR pairing, no 24h window, no templates); ingress at `POST /webhooks/bridge` verified by HMAC-SHA256 via env `WA_BRIDGE_HMAC_SECRET` (`convex/bridge.ts`). Managed provisioning: envs `WA_BRIDGE_DEFAULT_URL` + `WA_BRIDGE_ADMIN_TOKEN` (both set = "Servidor HNBCRM" default in the provisioning form — user only types a display name; admin token never leaves the server; advanced users can still point to their own gateway). Bridge is opt-in per org and carries a permanent-ban risk (unofficial protocol, violates WhatsApp ToS). Key files: `convex/bridge.ts`, `convex/lib/bridgeParse.ts` (pure parser), `convex/lib/bridgeSend.ts` (text), `convex/lib/bridgeMedia.ts` (media), `convex/lib/bridgeSession.ts` (QR/status/provisioning). Outbound dispatch in `convex/whatsapp.ts` branches by provider (voice notes are transcoded to ogg/opus via the Whisper service's `/convert`). Typing presence and delivery/read receipts flow both ways (`sendTypingState`, `markConversationRead`, `ChatPresence`/`ReadReceipt` webhook events). UI in `src/components/settings/ChannelsSection.tsx` (+ `ChannelHealthPanel` with 7-day delivery stats).

**Bridge — mensagem do aparelho, histórico e exclusividade do número (v0.56):** três coisas que faltavam para o inbox bater com a conversa real. (1) **`fromMe` entra como `outbound`:** o parser descartava todo `Info.IsFromMe` para evitar o eco do próprio CRM, mas o WhatsApp multi-device usa o MESMO evento para o eco e para o que um humano digita no app do celular — descartar os dois fazia a conversa divergir (e o atendente IA lia um histórico incompleto). Agora vai para `conversations.internalReceiveDeviceMessage` (`metadata.via:"device"`, sem `senderId`, NÃO mexe em `lastInboundAt`/`unreadCount`, NÃO enfileira a IA nem transcrição/visão; o eco morre na idempotência de `externalId`). O telefone sai do `Chat` (o `Sender` somos nós) e o `PushName` é descartado (é o nosso — renomearia o contato). Reação nossa e grupo seguem ignorados. (2) **Histórico do aparelho, POR NÚMERO, opt-in default OFF** (`channelConfigs.bridgeHistoryEnabled/Limit/Days`, 100 msgs/conversa e 7 dias): o wuzapi guarda as mensagens numa tabela própria quando o instance tem `history > 0`, e cada linha traz o evento whatsmeow ORIGINAL — a importação reusa `parseBridgeEvent` e o ingest inteiros, então re-sincronizar não duplica. `lib/bridgeHistory.ts` (puro) + `bridge.setBridgeHistoryConfig`/`syncBridgeHistory`/`internalImportBridgeHistory`; UI no card do número. **Importa só `fromMe`, de propósito:** a recebida sempre chegou pelo webhook, e reinjetá-la passaria por `internalReceiveMessage`, que enfileira o atendente — numa org em autopilot a IA responderia no WhatsApp a uma pergunta de dias atrás. **Pegadinhas do wuzapi medidas contra o gateway real** (fixtures nos testes): o campo é `data_json` (snake_case, o alias `datajson` só existe no SELECT interno); a coluna `timestamp` da linha é o instante da GRAVAÇÃO, não o da mensagem (num HistorySync as 50 linhas vieram com o mesmo carimbo sendo de meses atrás — a hora real sai de `data_json.Info.Timestamp`); conversa sem histórico devolve `{"code":200,"data":null}`, que tratado como erro fazia TODA a varredura falhar. O HistorySync sob demanda é best-effort de verdade (pedimos 100 e vieram 50, todas antigas). (3) **Um número = uma conta:** `channelConfigs.bridgePhone` (dígitos) + índice `by_bridge_phone` DEPLOYMENT-WIDE. O mesmo número pareado em duas orgs faz cada mensagem do contato ser ingerida nas DUAS — vazamento entre inquilinos, não só ruído. Ao ficar "connected", `claimBridgePhone` (dentro de `internalRecordHealthCheck`, MESMA transação, então não há janela com os dois ativos) desativa os outros canais com aquele número, audita na org DESLOCADA (severity `high`), pausa as campanhas dela e agenda `internalLogoutBridgeInstance` (`POST /session/logout` com o token da própria instância — desvincula o aparelho; `/session/disconnect` só derruba o socket e não serve). `deleteChannelConfig` também agenda o logout: era ELE que criava instâncias órfãs logadas para sempre. **Pegadinha decisiva:** `GET /session/status` devolve `jid: ""` mesmo logado (medido em 3 instâncias) — por isso `displayPhoneNumber` nunca era preenchido em canal bridge; o número sai de `GET /admin/users` (`phoneFromAdminUsers`), disponível só no gateway GERENCIADO, então em self-hosted a chave fica vazia e a regra não dispara. Aviso genérico no modal do QR antes de escanear (o número só é conhecido depois) + banner nomeando as contas deslocadas, sem auto-close. **(4) Correção de fundo:** `buildBridgeConnectRequest` mandava `Subscribe: ["Message"]` por padrão e o `Connect()` do wuzapi faz `UPDATE users SET events=$1` — todo reconnect REESCREVIA a assinatura feita no provisionamento, e por isso os recibos de entrega/leitura estavam mortos desde 2026-08-07 (todos os outbound travados em `sent`). Agora existe `BRIDGE_WEBHOOK_EVENTS`, compartilhada entre connect e provisionamento. Ops: `channelConfigs:internalResolveBridgePhone`/`internalBackfillBridgePhone`, `bridge:internalApplyBridgeHistoryConfig`. Testes: `bridgeDeviceMessages.test.ts`, `bridgeNumberExclusivity.test.ts`, `lib/bridgeHistory.test.ts`.

**Devolver à IA respondendo o que ela precisava (v0.50):** o fluxo "gerente responde ao atendente" — humano informa um dado (Pix, valor, data) e a IA continua o atendimento sabendo dele. (1) **Notas da equipe persistentes:** `conversations.aiTeamNotes` (cap 20, FIFO) — toda instrução de `returnToAi`/reject-com-instrução é gravada como nota e entra no prompt de TODOS os turnos seguintes da conversa como "INFORMAÇÕES DA SUA EQUIPE" (fonte oficial confirmada; a nota igual à instrução do turno atual é filtrada para não duplicar). (2) **Prompt reforçado:** os blocos de instrução/notas agora vencem explicitamente regras de PERSONA do tipo "você não sabe/não tem acesso/quem confirma é a equipe" (sem isso a IA recusava a informação que a equipe acabou de passar — caso real do Guardião) e proíbem `requestHandoff` para o que a instrução já resolve; só as REGRAS OBRIGATÓRIAS da plataforma seguem acima. (3) **`handoffs.rejectHandoff` aceita `instruction`:** rejeita + agenda `internal.attendant.internalQueueInstructedTurn` (via scheduler — import direto criaria ciclo handoffs↔attendant), que faz a devolução plena (despausa + lead de volta ao atendente) e dispara o turno instruído; a instrução vira `notes` do handoff. UI: popover de instrução (`AiInstructionPopover`, agora exportado de `AiDraftCard.tsx`, com `direction="up"`) no botão "Devolver à IA" do card em /app/repasses e no rodapé do `HandoffPeekSlideOver`. (4) **Correções:** núcleo único `queueInstructedAiTurn` em `attendant.ts` (item coach pendente convertido limpa `sourceDraftId`); `internalCommitAiReply` ganhou o mesmo bypass humano do claim (arg `humanInitiated`) e marca rascunhos `pending` antigos como `revised` ao enviar direto (sem órfãos no inbox); `returnToAi` sem mensagens não perde mais a instrução (nota persiste). Testes em `attendantCoach.test.ts` ("notas da equipe e devolver com instrução").

Guarda extra do commit: `conversation.lastInboundAt > runStartedAt` aborta com `cliente_falou` (o cliente escreveu enquanto a IA gerava) e devolve o follow-up a `scheduled`. **Coalescing — o turno REATIVO sempre vence:** `internalEnqueueFromInbound` e `queueInstructedAiTurn` chamam `yieldFollowUpItemToReactiveTurn` antes de sequestrar um item `pending` de origem `follow_up` — limpa `origin`/`followUpId` (vira turno normal) e devolve o follow-up a `scheduled` (+30min), NA MESMA transação; sem isso o item rodaria com o prompt de follow-up respondendo a uma pergunta nova e concluiria a tarefa sem tê-la feito. **Desfecho único** `resolveFollowUpOutcome` (`lib/followUpOps.ts`) — todo caminho terminal da fila passa por aqui (skip no claim, skip no commit, falha final, descarte de rascunho, watchdog): `done`/`not_needed` conclui a tarefa com comentário e webhook `task.followup_executed` (exceção DECLARADA a "agente nunca marca completed sozinho" do gap analysis — a tarefa é dela; `done` aceita `force:true` para reabrir um `needs_human` já terminal quando a entrega chega tarde); `needs_human` reatribui ao dono humano do lead (ou fica SEM dono, nunca de volta ao próprio agente IA) + notificação `ai_followup_needs_human` (mesma regra de destinatário de `createHandoffCore`, agora em `lib/notify.ts:inboxRepliers` — saiu de `handoffs.ts` porque os dois módulos se importariam em ciclo; `actorId` = quem PROVOCOU a escalada — quem assumiu a conversa não recebe aviso sobre a própria ação, só os demais destinatários do broadcast, se houver) + webhook `task.followup_needs_human`; `canceled` cobre opt-out/conversa arquivada/lead arquivado/tarefa excluída. ## Convex Rules (mandatory)

Rules from `.cursor/rules/convex_rules.mdc` and `.claude/convex-agent-plugins/rules/`:

- **Always** use new function syntax: `query({ args: {}, returns: v.null(), handler: async (ctx, args) => {} })`
- **Always** include `args` and `returns` validators on every function
- **Never** use `.filter()` on queries — use `.withIndex()` instead
- **Never** use `Date.now()` inside queries — breaks reactivity
- **Never** schedule `api.*` functions — only schedule `internal.*` functions
- Use `internalQuery`/`internalMutation`/`internalAction` for non-public functions
- Actions using Node.js APIs must include `"use node";` directive and be in a separate file
- Use `ctx.db.patch` for partial updates, `ctx.db.replace` for full replacement
- Index naming: `by_<field>` or `by_<field1>_and_<field2>`
- Use `"skip"` pattern: pass `"skip"` to `useQuery` when args aren't ready
- Keep query/mutation handlers thin — extract business logic into plain TypeScript functions
- Use cursor-based pagination (`paginationOptsValidator`) for large datasets
